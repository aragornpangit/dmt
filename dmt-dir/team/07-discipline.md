# 工程纪律

## Git 与工作区

开发线按三级分权（完整拓扑见 [`01-org.md`](01-org.md)）；一个实施单元一个隔离 worktree（独立 index）+ 独立分支，并行单元不共用同一 index。

1. `dmt-de`（工程师）：在自己 worktree 的功能分支上实施、测试、自审并 commit，只列自己获授权的路径；不 merge、不 push、不改共享分支。功能分支上的 commit 不进主干，是后续评审的不可变对象。
2. `dmt-dl`（队长）：派未参与本单元实现的临时子代理，基于该功能分支的 commit 独立评审，通过后汇总上报；不代工程师 commit，不 merge、不 push。
3. `dmt-dm`（经理）：按项目 Git 策略和授权执行 merge、push、发布或回滚；不直接实施。

`git add` 只写本 worktree 的 index，不跨 worktree 交接；分支是仓库共享 ref，worktree 只签出其中一条 —— 交接靠功能分支上的 commit，不靠暂存区。提交前检查工作区状态，不用宽泛暂存覆盖他人改动。冲突需逐文件理解两侧改动，不能只因一侧更新就整份覆盖。清理工作区、分支或进程前确认所有权和未完成工作，不使用模糊匹配杀死进程。

## 并行与派发

1. 无依赖的工作单元一律并行派发：优先用 workflow（动态编排）或一次性开满当前环境可用的多个 subagents；只有真依赖、共享文件 / 构建目标 / 设备或顺序验收才串行，并在回报里写明理由。
2. 先分析依赖；共享文件、构建目标、设备和有顺序要求的验收需要协调或串行。
3. 派发写清输入、边界、产物、判据、回报和必要的时间预算；新工作单元使用新上下文。
4. 谁派发谁汇总；子代理只向派发者回报，不越级传递未经核验的结论。
5. 需要等待时使用平台原生通知或等待原语，避免无意义轮询。
6. 开发线内部（`dmt-dm` ↔ `dmt-dl{n}`）的派单、工作安排、进度与结果回报由开发线自行闭环，不需 `dmt-dir` 确认；只有需求 / SPEC 或验收口径变化、以及跨域冲突才上交（见 [`01-org.md`](01-org.md)）。

## 评审与证据

1. 实现与独立评审分离；评审只依据需求、变更和可复现证据。
2. 每条判据都有 PASS / FAIL 与证据；无证据、证据过期或范围不符不能判 PASS。
3. 验收范围以票面判据为准，不额外设置抽检环节。
4. 需求、调研和代码的批准人按项目授权确定，格式检查不能替代实质验收。
5. 性能或实验结论注明环境、窗口、构建和对照条件；不同条件的数据不直接比较。
6. 共享设备或外部系统写操作由获授权者执行，并记录版本、结果和必要的清理状态。
