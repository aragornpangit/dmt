# 命名约定

项目已有命名规范优先；没有时再采用本约定。

- 文件名应能识别产物类型、主题和版本，使用简短 slug，避免无意义编号堆砌。
- 需求、规格、工单和测试使用稳定标识互相引用；重命名时保留可追溯关系。
- 小修可原地更新；实质修订按项目版本策略处理，并标明替代关系。
- 新增件按本格式；历史件不因规则变化反复改名，需要迁移时一次性完成并保留追溯。
- 运行时消息与正式产物分开命名，消息序号不得重用。

## SPEC、工单与证据的编号（`{spec-seq}`、`{ticket-seq}`、`{evidence-seq}`）

- SPEC 用纯号 `{spec-seq}`（一条需求的「链」号）。有父 SPEC 的工单序号是两级复合值 **`{spec-seq}.{NN}`**：`.` 是层级分隔符（非小数点、非版本号），前半是所属 SPEC 号，后半是该 SPEC 下的第 NN 张工单。例 `089.02` ＝ SPEC-089 的第 2 张票。
- SPEC：`{seq}-spec-{slug}-{YYMMDD-HHMM}-V{N}.md`。
- 有父 SPEC 的票：`{seq}.{NN}-ticket-{slug}-{YYMMDD-HHMM}-V{N}.md`，票面「票号」写 `{seq}.{NN}`；`.` 只在编号段出现一次（扩展名 `.md` 除外），slug／时间戳仍用 `-`。
- 无父 SPEC 的票（门治理、取证、勘误、审计修复等）：`{seq}-ticket-{slug}-{YYMMDD-HHMM}-V{N}.md`，票号写 `{seq}`，不带 `.NN`；`{seq}` 是独立的全局工单序列，不与 SPEC 号共享计数。
- 历史件迁移（一次性，不适用于新项目）：`-NN` 子票已统一改为 `{seq}.{NN}-ticket-{slug}-{YYMMDD-HHMM}-V{N}.md`，与普通子票同空间；原 NN 已被占用时顺延到该 SPEC 的下一个空号，票面 H1 保留「原编号 `{seq}-{NN}`」以便追溯。
- `NN` 从 `01` 起、**只在同一 spec-seq 内自增**，不同 SPEC 各自从 01 计数；作废票的 NN 不回收、不重用。某 SPEC 的历史首票若无 NN，视作 `.01`，其后新票从 `.02` 起。
- 时间戳统一 `YYMMDD-HHMM`；历史件只有日期、没有 HHMM 的，迁移时用该文件 git 首次提交时间补齐。
- 证据单元用 `{seq}.ev{NN}-{slug}-{YYMMDD-HHMM}`（目录或文件）：`ev` 是证据空间，与工单 `.NN` 区分；`NN` 从 `01` 起、同一 SPEC 内自增。
- SPEC 的纯号只归 SPEC：有父 SPEC 的工单用 `{spec-seq}.{NN}`，不再占用纯 `{spec-seq}`；无父 SPEC 的工单用独立的全局工单序列 `{seq}`，与 SPEC 号不共享计数。有父票的票面须显式写「对应 SPEC：`{seq}`」建立追溯，不依赖同号隐式关联。
- 迁移完成后只向前生效：新增件按本格式，不再使用 `--v`、`-v` 或裸 `-NN` 写法；历史件已完成一次性改名，不再回溯。

可选 DMT 形式为 `<id>-<type>-<slug>-<YYMMDD-HHMM>-V<N>.md`；id 位数和版本形式可由项目覆盖。收件箱命名见 [`../ops/comms.md`](../ops/comms.md)。
