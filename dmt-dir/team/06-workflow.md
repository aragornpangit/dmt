# 通用工作流

1. **澄清**：确认目标、范围外、约束、产物和验收口径。
2. **设计**：形成与现状一致的方案，标明关键决策、依赖、风险和测试接缝。
3. **拆分**：按可独立验证的纵向单元分工，明确输入、文件边界和依赖关系。
4. **研究与定义**：存在选型、复用、竞品或架构不确定性时，AM 派多个 AE 取证并汇总 `docs/analyst/` 报告（含 Proposal）；DIR 据用户需求和报告写 PRD，PDE 据已批准 PRD 用 `to-spec` 写 SPEC，DIR 审核批准后才交开发线。
5. **实施**：DM 先创建隔离 worktree，DE 在分配工作区做最小充分改动，运行相关测试并保留真实结果和 commit。
6. **评审**：由未参与实现者先取本地规范基线（`dmt-reviewer/references/`，不联网检索），再跑 `dmt-dir/scripts/review-gate.sh`（类型检查 → lint → 测试），最后按 ticket 判据审核指定 commit 和 diff；静态门任一段 FAIL 或判据不满足即 FAIL 返回实现者。
7. **整合**：DM 获授权后 merge、push，记录 ticket 完成字段；失败不得标 `DONE`。
8. **收口**：向派发者交付产物、证据、变更摘要和未决项。

## 产物最小字段

- PRD（`dmt-dir` 起草）：上游用户需求、调研报告引用、问题、用户与场景、方案、用户故事、验收标准、范围外、开放问题。
- SPEC（`dmt-pde` 起草）：批准的 PRD 与调研报告引用、Proposal 采纳或拒绝理由、目标、方案、实现决策、验收标准、测试接缝、范围外、依赖。
- 工单：目标、输入、验收判据、文件边界、依赖、状态、验证要求、`review_commit`、`merge_commit`、`push_remote`；涉及硬件时另含设备标识、启动方式、退出验证与设备状态证据。
- 调研（`dmt-am` 落盘 `docs/analyst/`）：问题、结论、来源或可复现命令、证据分级、限制、对比、Proposal（建议、取舍、风险、待决项）。

这些字段可按项目模板调整；格式完整不能替代内容可验证。
